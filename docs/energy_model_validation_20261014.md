# 固定脚でのエネルギー計算とブレーキ応答の検証

## 調べること

各ZEROクロスで、必要なエネルギー変化を逆算できているか、入力時間の上限でそれを出せないのか、選んだ入力の後に予測どおりのピークへ到達するかを分けて確認する。今回は前後移動を固定した左右揺動を対象とする。

1. `E_free`：そのZEROクロス状態から、入力せずに到達すると予測したピークの位置エネルギー。無入力時の実測値ではない。
2. `unclamped_energy_request_j = E_target - E_free + bounded_I - bias`：制限前に加えたい仕事。負なら取り除きたい量。
3. `q_unclamped_mA_s`：その仕事から求めた、上限適用前の符号付き電流積算量。二次式に実数解がない場合はnullで、`unclamped_inverse_valid=false`。この場合も既存の制限付き計算は動作する。
4. `commanded_energy_deficit_j` / `q_ff_energy_mA_s`：制限後に逆算した仕事と電流積算量。`q_command_mA_s` / `pulse_width_ms`：整数ミリ秒で実際に選んだ入力の予測積算量と時間。
5. `maximum_input_work_j`：その側で許可された入力時間と電流、またはブレーキ曲線の頂点で制限される最大仕事。負なら除去可能な仕事。
6. `unapplied_energy_request_j`：制限前の仕事から、実際に選んだ入力のモデル上の仕事を引いたもの。負なら取り除けないと予測したエネルギーが残る。これは実測損失ではない。
7. `predicted_energy_j` と次の対応する `measured_energy_j`：選択した入力を使った予測と、MEKFのピーク角を機構の位置エネルギー式へ変換した結果。後者は独立したエネルギー計測ではなく、姿勢推定と幾何モデルの精度に依存する。

1.0.5以前の `q_unclamped_mA_s` には制限後の値が記録されていた。1.0.6の `energy_request_audit_revision=unrestricted_inverse_v1_20261014` から意味を修正した。古いログを解析する際は、この値を信用せず制限前の仕事から再計算する。

`predicted_current_goal_mA`、`predicted_current_rise_tau_s`、`aligned_initial_current_mA` も記録する。これらから、上限とは別に必要時間が100 ms以内に存在するかを後処理で求める。解が100 msを超える場合や逆算が成立しない場合、具体的な必要時間はnullとする。実機でその長い入力を実行するものではない。

## 最初の測定

- 同じファームウェア1.0.6、固定脚、目標8°、指令300 mA、ZEROクロス入力を使う。
- 「予測誤差の学習補正」を「使用しない（エネルギー式の検証）」にする。学習とその補正入力だけを止める。左右の積分補正は従来どおりで、ログに記録する。
- 負側ブレーキ上限を20・50・0 msで各3回測る。例えば `20→50→0→50→0→20→0→20→50` の順にし、順番と経過時間の影響を小さくする。
- 50 msは上限であり、実際の入力時間はエネルギー計算に決めさせる。0 msでも正側の加振と始動キックは実行する。
- 0 msは負側のブレーキだけを止める。負側にエネルギーが不足した周期では加振することがあるため、`pulse_width_ms=0` の周期だけを負側の無入力データとして扱う。
- 開始前に機体とホイールの回転が落ち着いていることを確認し、固定方法や重心位置をそろえる。開始直後のホイール回転数と電池電圧もログで照合する。
- 測定時間はまず15秒。各回のRWLOGを保存し、途中停止した試行も残す。

まず5秒以降の共通区間を比較するが、これは定常状態の成立を保証しない。各イベントの推移、最後の区間、試行ごとの平均を併記する。学習補正を切るため、補正発動を待つ条件は不要である。

## 判定

必要量に対して選択入力が小さく、飽和フラグと取り除けない予測エネルギーが残るなら、上限が制御を制限している。上限に達していても、予測したピークと実測ピークの差は別に評価する。上限による到達不能とモデル誤差は同時に存在し得る。

予測と実測がずれた場合は、次の順に調べる。

1. 実電流の立ち上がりが予測電流と合うか。電流は目標値に即座に達しない。観測電流積分はパルスの端の区間を含まない診断値なので、予測Qとの差をそのまま総入力の誤差とはしない。
2. 0 ms条件で無入力のエネルギー予測が合うか。
3. 無入力側の誤差を踏まえて、ブレーキの仕事の予測が合うか。
4. 同じZEROクロス角速度でも、ホイール回転数や電池電圧で誤差が変わるか。

ブレーキ側だけの誤差を調べるには、0 msとブレーキありの条件で開始状態が重なる必要がある。初期の探索では角速度差3°/s以内、ホイール回転数差50 rpm以内、電池電圧差100 mV以内を比較候補にし、差そのものも残す。これらは暫定の選別幅で、状態が同じことや因果関係を保証しない。重なるデータがなければ、式全体の誤差だけを報告し、ブレーキ係数を同定したとは扱わない。無入力時の損失とブレーキ仕事を分離できる状態で、複数の異なる入力が必要になる。

負側ピークの後の正側ZEROクロス速度、正側ピーク、100 ms上限への到達も確認する。負側が8°へ近づいても、その次の正側が小さくなる可能性がある。

## ホイールと電流の記録

入力前の回転数・実電流と、ピーク確認時の回転数・実電流を記録する。ピーク確認時の値は幾何学的なピークそのものの時刻ではない。`peak_telemetry_capture_time_ms` と `peak_speed_age_us` / `peak_current_age_us` を確認し、古いデータは比較から外す。回転数から角運動量・回転エネルギーを求めるには、ホイール慣性が別に必要である。

実電流は既存の時系列と独立したサンプル時刻・連番を使う。同じサンプルが複数のログ行へ転記されることがあるので重複を除く。今回追加したピークの記録は既存テレメトリのコピーであり、制御中の新たなモータ通信を増やしていない。

## 解析

```sh
python tools/analyze_energy_validation.py run_20ms.rwlog run_50ms.rwlog run_0ms.rwlog --out work/energy_validation
```

解析はCRC検証付きでログを展開し、各入力と次の同側ピークを対応づける。`events.csv` に制限前の仕事・入力、実際の入力、未実施の仕事、予測と実測の差、電流・ホイール情報を残す。`summary.json` / `summary.csv` は試行と側ごとの要約である。過去の変換済みログフォルダも入力できる。この解析だけでブレーキの独立した仕事を測定したとはしない。

## 現時点の記録から分かること

最新5試行の20 ms条件では負側55イベントすべてが上限で制限された。除去できないと予測したエネルギーの試行平均は0.301～0.392 mJ。未補正モデルと実測の残差は平均−0.071～−0.139 mJで、上限による不足とモデルのずれが両方ある。

以前の50 ms条件では、負側の実際の入力は26～50 msで、12イベント中上限到達は1回だった。一方、正側は11回すべて100 ms上限に達していた。これは現在の版で再測定する必要がある。無入力側の損失誤差とブレーキ仕事の誤差は、まだ独立して確定していない。
